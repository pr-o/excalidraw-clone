# Multi-Element Resize — Design

**Date:** 2026-09-19
**Status:** Approved
**Scope:** Dragging a handle on a multi-element selection's combined bounding box scales the whole group together — position, size, and (for text) font size all scale proportionally. No group rotation, no frame-membership recomputation, no affine shear for mixed-rotation selections.

## Problem

The Stats Panel spec (2026-09-18) identified this exact gap and explicitly deferred it: "No multi-element group-scale transform exists. `resize.ts`'s `computeResize`/`buildResizeMoveEffect` operate on a single `elementId`; there is no 'scale N elements together from one bounding box' logic anywhere." This spec builds that transform.

Two structural facts confirmed during exploration:

- **Multi-selection already renders resize/rotate chrome per element, but none of it is hittable.** `packages/renderer/src/overlay.ts`'s `drawSelectionChrome` loops every selected element and draws its own full outline + 8 handles + rotation handle. `packages/tools/src/tools/selection/handles.ts`'s `findHandleAt` immediately returns `null` when `selectedIds.length !== 1` — so today's multi-select handles are pure decoration with no drag behavior behind them.
- **Group membership is already resolved before the tool layer sees a selection.** Clicking one grouped element expands the selection to the whole group via `expandIdsToGroups` in `apps/web/src/components/App.tsx` and `useDrawingDriver.ts`, before `selectedIds` ever reaches `resize.ts`/`handles.ts`. The resize transform itself does not need to be group-aware — it operates on whatever `selectedIds` it's handed, the same way `flipElements` already does for Ctrl+G groups today.

`flipElements` (`packages/scene/src/flip.ts`) is the direct precedent for "one transform, applied per-element, repositioned relative to a combined-selection anchor" — this spec's transform follows the same shape.

## Decisions

- **New pure function `resizeElements(elements, ids, originBounds, newBounds)` in `packages/scene/src/resize-group.ts`** (new file, alongside `flip.ts`), returning full replacement elements for the closure of `ids`. Locked and deleted elements are filtered out defensively, mirroring `flipElements`' `!e.isDeleted && !e.locked` filter (in practice unreachable today, since locked elements can't be selected — `useDrawingDriver.ts` skips them at hit-test — but kept for the same reason `flipElements` keeps it: cheap insurance).
  - Scale factors: `sx = newBounds.width / originBounds.width`, `sy = newBounds.height / originBounds.height`. **If `originBounds.width` (or `.height`) is `0`, that axis's scale factor is forced to `1`** — guards a perfectly flat line, a single-point freedraw stroke, or any other zero-extent member of the selection from producing `Infinity`/`NaN` through the division. This is designed in up front, not discovered after the fact: the Stats Panel final review just caught a closely related class of bug (line/arrow/freedraw geometry invariants) that no per-task review saw coming.
  - **Rectangle-like elements** (`rectangle`, `diamond`, `ellipse`, `triangle`, `parallelogram`, `hexagon`, `pentagon`, `octagon`, `image`, `frame`): position scales relative to `originBounds`'s top-left — `x' = newBounds.x + (x - originBounds.x) * sx`, same for `y'` — and `width' = width * sx`, `height' = height * sy`. `angle` is untouched (see the rotated-elements decision below).
  - **`line` / `arrow` / `freedraw`**: position scales the same way as above. `points` (stored relative to the element's own `x`/`y`) are scaled by `(sx, sy)` componentwise. `width`/`height` are then **recomputed from the scaled points' bounding box**, not simply multiplied by `sx`/`sy` — this keeps the width/height-mirrors-points invariant intact, the exact invariant the Stats Panel final review caught the app breaking for direct width/height edits on these types. Existing bindings (`startBinding`/`endBinding`) are left untouched; a bound arrow's endpoints move with its own points scaling, and if its bound element is also in the resized selection, both move together, keeping the visual connection intact without any special-case binding math. If the bound element is _not_ in the selection, the arrow's endpoint can end up visually detached from it after the resize — a pre-existing category of edge case (the same thing already happens today if you drag-move a bound arrow without its bound element), not something this feature introduces or needs to solve.
  - **`text`**: position/box scale like rectangle-like elements. `fontSize` scales by `sy` (the vertical axis, since font size is fundamentally a vertical measure — matches real Excalidraw's approach for the common case where a text box is stretched more in one axis than the other), clamped to a minimum of `4` (mirrors the existing min-1 clamp pattern used for width/height elsewhere in the codebase, scaled up since a font under a few px is unreadable rather than merely small).
  - **Bound text labels are excluded from direct transformation.** A selected `text` element whose `containerId` refers to another element _also in the selected set_ is a passenger, exactly like `isPassengerLabel` in `flip.ts` — it is dropped from the map/transform entirely. `reconcileBoundText` (already invoked unconditionally inside `Scene.mutate`) re-lays it out against its container's new box automatically after the mutation; transforming it directly here would be redundant, conflicting work racing against that reconciliation. A selected standalone text (no `containerId`, or its container isn't in the selection) is treated as an ordinary text element and gets the position/box/fontSize scaling above.
  - **Rotated elements keep their own `angle` unchanged.** No affine shear is computed for mixed-rotation selections — this matches the precedent already set by `flipElements`, which repositions each element's center relative to the combined bounds without altering rotation math. A rotated rectangle in a resized group may look slightly different from real Excalidraw's true-shear behavior at extreme aspect-ratio changes; this is an accepted, documented simplification, not a bug.
  - **Frames are treated as plain boxes.** A frame's `x`/`y`/`width`/`height` scale like any rectangle-like element. Frame membership (which elements are visually "inside" a frame) is computed by geometric containment elsewhere in the codebase and is simply re-derived after the mutation, the same way it already is after any other move/resize — no new frame-specific logic is added here.

- **`packages/tools/src/tools/selection/handles.ts`**: extend `findHandleAt` with a branch for `selectedIds.length >= 2` (the current single-selection path is untouched). Compute the combined AABB via the existing `getElementsBounds` over the selected non-deleted elements, and hit-test its 8 corner/edge points — no rotation handle for the group box (out of scope, see below). Returns a new `HandleHit` variant `{ kind: "groupResize"; handle: ResizeHandle; ids: readonly string[] }`.

- **`packages/tools/src/tools/selection/index.ts`**: a new drag state parallel to the existing single-element `resizing` state, carrying `ids: readonly string[]` and `originBounds: ResizeOrigin` (the combined-AABB snapshot, `angle: 0`) instead of a single `elementId`/per-element origin. The existing `computeResize` function is reused unchanged — it already operates generically on a `{x,y,width,height,angle}` box and a handle, so a synthetic group box requires no changes there. On move, `computeResize` produces the new box; `resizeElements` (above) turns `(elements, ids, originBounds, newBox)` into the mutation. Commit/revert follow the same shape as the existing single-element `buildResizeCommitEffect`/`buildResizeRevertEffect`, generalized to a list of ids. Shift-drag aspect lock falls out for free, since it's the same shared `computeResize` logic.

- **`packages/renderer/src/overlay.ts`**: for `selection.length >= 2`, keep the existing per-element chrome loop (thin outline only — this already exists via `drawElementChrome`'s per-element path, so "keep" here means the existing individual-outline drawing needs to _stop_ drawing that element's own 8 handles + rotation handle when the selection has 2+ members, since those aren't hittable and shouldn't imply they are), and additionally draw **one** combined-bounds box with 8 handles on top, computed the same way as the new `findHandleAt` branch. For `selection.length === 1`, nothing changes — existing per-element chrome (including the rotation handle and linear-element point/bend handles) stays exactly as today.

## Testing

Unit TDD: `packages/scene/test/resize-group.test.ts` (new) covering `resizeElements` — generic rectangle-like scaling from each of the 8 handle directions, the line/arrow/freedraw points+width/height invariant after scaling (asserting `width`/`height` match a fresh bounds computation over the scaled `points`, not just the multiplied value), text `fontSize` scaling and its minimum-4 clamp, bound-text-label exclusion (asserting a passenger label's fields are untouched by `resizeElements` itself, separately from `reconcileBoundText`'s own existing test coverage), locked/deleted filtering, and the zero-width/zero-height origin-axis guard (a degenerate single-point element in the selection must not produce `NaN`/`Infinity` in any output).

`packages/tools/test/selection-handles.test.ts` (extend): combined-bbox hit-testing at each of the 8 handle positions for a 2+ element selection; a regression case confirming single-selection hit-testing (resize, rotate, linear endpoints/bends) is unaffected by the new branch.

`packages/tools/test/selection-resize.test.ts` (extend): the group-resize drag/commit/revert state-machine path, including Shift-aspect-lock, mirroring the existing single-element test shapes.

No new renderer unit test — matches existing precedent (`overlay.ts` has no unit tests today; canvas drawing is verified via e2e).

E2E (new spec): multi-select two rectangles, drag a corner handle, assert both scale proportionally and the result persists to `localStorage`; multi-select a rectangle and a line, drag a handle, assert the line's `points` scaled and its `width`/`height` remain consistent with a fresh bounds computation over those points (a direct regression guard for the exact invariant this design protects, and the same class of bug the Stats Panel final review caught).

Full gate (`typecheck`, `test`, `format:check`, `lint`) plus full e2e suite before merge, per this repo's established convention.

## Out of scope (follow-up candidates)

- **Group rotation** (a rotate handle for the combined bounding box) — not requested for this pass; the single-element rotate handle is untouched.
- **True affine shear for mixed-rotation group resize** — each element keeps its own `angle`; only position and size scale. Accepted simplification, matches the `flipElements` precedent already in the codebase.
- **Frame-membership recomputation as part of resize** — a frame resizes as a plain box; which elements are geometrically "inside" it afterward is derived by existing containment logic, not by any new logic in this feature.
- **Re-anchoring arrow bindings whose bound element is outside the resized selection** — a pre-existing category of edge case (already present for plain drag-move today), not solved or worsened by this feature.
- **Smart/alignment guides and comments/annotations** — unrelated gaps from the same original codebase audit, not picked for this pass.
